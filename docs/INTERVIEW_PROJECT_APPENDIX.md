# 项目说明与个人实践复盘

您好，感谢您查看这个项目。

这是我围绕《三角洲行动》玩家组队与游戏服务需求，借助AI工具逐步制作的个人实践项目。仓库包含网站前后端、数据库结构、测试及运行工具；目前已部署过受限云端测试环境，付费业务使用模拟资金。

我的编程基础仍然有限，复杂代码实现和技术检查主要借助Codex、Claude等工具完成。我主要投入在产品构思、业务规则、功能取舍、实际使用反馈和项目推进上。这份说明希望介绍网站背后的思考，以及我在制作过程中承担的工作。

## 从什么需求出发

我关注的是玩家寻找合适队友时的沟通成本：游戏模式、玩法偏好、在线时间和语音习惯不同，单纯找到一个人，并不等于能顺利组成队伍。

因此，我希望网站能把玩家资料、筛选条件、招募申请和小队沟通衔接起来，让玩家从表达需求走到确认组队。在此基础上，再探索与付费游戏服务的衔接。这个方向目前仍是个人产品构想，后续需要通过真实用户反馈检验。

## 我怎样构思业务流程

免费组队和付费服务围绕不同的使用目的展开。

免费组队采用“选择端游或手游—展示名片与招募—提交申请—确认成员—小队沟通”的流程，不需要经过付款或创建零元订单。针对端游与手游的玩家差异，我提出分区和信息隔离，同时优先复用现有页面与后台逻辑，减少重复维护；当前不再细分QQ、微信渠道。

付费服务则围绕订单履约设计：

**选择服务与需求 → 创建订单与模拟付款 → 匹配接单 → 必要参与者确认开始 → 计时与对局记录 → 完成确认及评价，或进入售后。**

我特别关注流程中的例外情况。例如，等待匹配不应消耗服务时间；对局结果需要另一方核对；首局符合条件的免费换人只能使用一次。换人后仍在等待新服务者时，消费者可以取消并全额模拟退款；新服务者已经接单后，则按协商或售后流程处理。这些选择需要同时考虑消费者体验、服务者履约预期和规则是否容易被反复利用。

## 我在制作中实际做了什么

推进过程中，我持续补充需求、确定阶段重点，并实际打开页面试用、整理反馈。已有反馈涉及标签选中不明显、消费者与服务者视角混淆、订单详情和操作入口不清晰，以及单方登记对局结果影响消费者使用换人权益等问题。

对于换人流程，我关注的不只是按钮能否点击，还包括谁有权登记、谁来确认，以及双方意见不一致时怎么办。后续实现允许实际参与者登记结果，由另一方核对，并保留售后入口。对于双身份设计，我要求页面能清楚区分使用视角，同时仍由服务端按实际订单关系判断权限。

在功能逐渐增加后，我也调整了投入方向：先核对已经完成的成果，保留成熟的名片、招募和原有页面，当前优先推进免费组队及公测准备，暂停新增收费功能。现有商业代码和历史数据保留，为后续发展留出空间。

为了便于项目展示，我提出将招聘专用入口调整为原站游客选项，让访问者能实际操作免费组队和模拟订单。这项调整也需要保留访问限制，避免为了演示方便而让游客取得管理权限。

## 我怎样使用Codex与Claude协作

我通常先向Codex说明需求、业务规则和修改范围，由它在现有项目中辅助实现、排查和执行回归检查；再将整理过的源码与具体检查目标交给Claude，从独立环境和使用路径进行复核。我的工作是组织任务、提供使用反馈，并结合业务目标判断哪些建议值得实施。

例如，Claude曾在隔离环境使用合成账号检查订单创建、模拟支付、接单、开始服务、对局核对、尾局、完成和评价，还检查重启后的记录保存及无关用户的访问限制。Codex随后逐项核对发现、完成必要修补并进行本地验证。

另一次售后专项复核涉及双方补充材料、管理员提出方案、用户异议、重新提案及模拟退款。其中，“用户必须明确选择接受方案或提出异议”成为一项具体改进：提交逻辑不能在意见缺失时默认用户接受，需要给出提示并等待明确选择。它体现了我在项目中逐渐重视的问题——流程能结束，还需要确保每一步正确表达参与者的意愿。

这种协作帮助我将实现、复核、修改和反馈连接起来。具体技术操作由工具辅助完成，涉及业务目标和取舍的判断仍需要我参与。相关检查使用合成账号和模拟资金，部分时长由测试时钟加速；已有局部复核不能视为完整真人验收。

## 当前完成情况与运营安排

网站已具备免费组队、端游/手游名片与招募隔离、站内账号及游客身份，以及模拟订单、匹配、计时、评价和售后等流程。主要技术包括HTML、CSS、JavaScript、Node.js、SQLite和Better Auth。当前代码已有自动化测试、格式检查和GitHub CI，具体记录与复现方式见[验证说明](VERIFICATION.md)。

目前仍处于受限测试与项目展示阶段，真实用户的持续使用和市场效果尚待验证。

我目前仍在校学习，近期还有考试任务，尚未抽身完成经营主体登记、网站备案和实际业务所需的资质、渠道准入准备。因此，当前不启用真实收付款，也未正式接入QQ、微信登录及真实邮件、短信投递渠道。站内账号密码、会话和游客功能已通过实际代码实现，外部渠道的申请与联调仍需继续推进。

正式交易还涉及商户准入、退款对账、服务者结算和争议责任，需要与经营及运营条件一起准备。计划在2026年10月底开始推进主体登记、备案材料和渠道准入核实；公开测试与正式运营时间将根据实际办理和验收结果确定。
