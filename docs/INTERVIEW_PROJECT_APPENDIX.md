# 附录：项目参与、订单流程与实际决策

整理日期：2026-10-17。依据项目聊天、用户实操反馈记录和当前源码编写，供项目评审与面试交流使用。第一人称段落是基于已发生工作的讲述示例，使用者应按自己的理解表达，不把文字熟练程度当作能力证明。早期原始聊天、反馈Word和含私有信息的运行材料未上传；本附录属于维护者整理的说明，可与代码、测试和[公开迭代记录](ITERATION_HISTORY.md)交叉查看。

## 一、我在这个项目中做了什么

> 我从《三角洲行动》玩家找队友、沟通玩法需求的场景出发，设计了免费组队和游戏服务匹配平台。我主要负责产品定位、流程和规则取舍、任务优先级、实际使用反馈，以及组织验证和部署；代码实现与大量技术检查由Codex、Claude等AI工具辅助完成。
>
> 我做过的判断包括：免费组队先于新增收费功能；端游和手游需要隔离，但不再细分QQ、微信；保留现有成熟页面；将招聘专用入口改为原站游客选项；付费链路允许模拟展示，但不接真实资金。项目已具有前后端和持久化业务流程，真实用户、正式渠道和合规运营条件仍有不足。

这些职责可以进一步区分：

| 我的实际参与 | AI及工具承担 | 尚未具备的事实 |
| --- | --- | --- |
| 提出需求、确认规则和范围，试用页面并反馈问题，决定是否继续开发、授权发布 | 按要求实现代码、执行自动化测试与命令、生成候选与部署校验记录 | 独立手写全部源码、真实支付接入、规模化用户运营和商业收入 |
| 发现展示和真实使用的差别，要求可操作游客体验，纠正GitHub连接器排查方向 | 实现游客身份及权限保护，检查安装状态和实际写入，上传源码并核对文件 | 真人跨设备全链路验收已完成、所有普通浏览器均可直接访问 |

## 二、不看稿时，先把订单讲成一条业务链

讲述时可以先固定一个场景：**单个消费者购买一名服务者的一小时服务，以下全部是模拟资金**。项目还支持多人参与分支，不能把两人示例当作全部规则。

> 用户先选择服务和需求，系统生成订单，保留当时的商品与规则信息。模拟付款成功后才进入匹配。服务者接受后先进入准备阶段，消费者和实际服务者确认开始后才计时，等待匹配不算服务时间。
>
> 服务过程中，一方可以登记对局和结果，但不能自己报告、自己确认；另一方要核对。有符合条件的首局未撤离记录时，消费者可以使用一次免费换人，新服务重新确认开始并计满时长。如果仍在等替换服务者，消费者可以取消并全额模拟退款；新服务者已经接单，则转协商或售后。
>
> 到约定时长时，已开始的尾局需要结束，不能继续开新局。对局结果核对完成后，实际参与者确认完成，再进入评价。出现争议就进入售后，核实材料、提出处理方案、回应或申诉，不能靠一次差评或者AI判断直接处罚、退款。

具体追问可按下面这张表展开：

| 环节 | 实际动作和控制 | 可以指向的实现 |
| --- | --- | --- |
| 建单 | 商品、价格、规则信息进入订单；请求做重复提交及版本控制 | [createMarket及command](../server/market.mjs) |
| 模拟支付 | 提交付款任务；处理结果再更新支付和业务状态，点击按钮不等于付款成功 | [payment-journal](../server/payment-journal.mjs)、[operations](../server/operations.mjs) |
| 匹配与接单 | 检查实际参与关系、接单资格和冲突，防止接自己的单及重复接单 | [订单模块](../server/market.mjs)、[参与者规则](../dist/order-participants.mjs) |
| 准备与计时 | 全部必要参与者确认后起算；浏览器倒计时不能作为结算依据 | market中的`start`、`serviceSeconds` |
| 对局与换人 | `endRound`记录报告人；`confirmRound`限制自确认；`firstSwap`只在符合条件时执行 | [售后资格判断](../server/aftercare.mjs)、market相应分支 |
| 结束与评价 | 到时后只处理已有尾局；存在未核对结果时不能确认完成；评价有权限与状态限制 | market中的`finish`、`review` |
| 售后与退款 | 材料、方案、同意或申诉各自留痕；权限和退款任务由程序检查 | [售后说明](../server/aftercare.mjs)、[订单测试](../tests/market.test.mjs) |

免费组队有自己的闭环：渠道选择→名片/招募→申请→确认成员→小队沟通→结束及反馈，不需要生成零元订单或经过付款流程。

## 三、我做过的四个具体取舍

### 1. 首局换人后的等待，可以取消；已经重新接单，走协商或售后

我明确确认过：首次换人后还没有新服务者接单，消费者可以取消并全额退款。原服务时间作废，不能让用户在等待时继续消耗权益；但新服务者已接受后，双方已经重新形成服务关系，不能继续套用同一个直接取消入口。

取舍是同时照顾消费者等待成本与服务者的履约预期。免费换人仅一次，避免反复刷新权益；正常对局失败也不能直接判定服务者过错。具体已实现分支见market的`cancel`、`firstSwap`及[相关测试](../tests/market.test.mjs)。这里的退款仍是模拟结果，真实收款前还需明确成本承担和渠道条件。

### 2. 一个账号有两种使用视角，权限仍按实际订单关系判断

消费者和服务者可以是同一个账号的不同使用视角。我反馈过身份切换后两类面板同时出现，以及订单详情和操作混淆的问题，要求用户看得清自己正以什么身份操作。

界面上只显示对应内容，服务端仍检查实际消费者、当前服务者和管理权限。页面切到“服务者”不会自动取得某笔订单的操作权。这样保留双向服务构想，也减少重复注册账号的成本。相应逻辑可查看[参与者规则](../dist/order-participants.mjs)和订单模块。

### 3. 免费组队优先，商业系统保留，但不继续扩收费业务

我在成熟度评估后要求停止没有实际依据的功能扩展，先完善免费组队、公测交付和运营条件；原有付费页面、订单代码和历史数据保留。后来为项目展示，允许游客操作模拟付费功能，但仍没有授权真实扣款或正式运营。

保留代码不代表允许对公众经营。这项取舍减少当前投入与管理复杂度，也保留后续扩展能力。能展示订单闭环，不代表已经验证盈利模式。范围和限制见[项目状态](PROJECT_STATUS.md)及[公测门禁](PUBLIC_BETA_GATES.md)。

### 4. 端游和手游要隔离，复用现有流程，不再细分QQ与微信

我提出免费招募应覆盖手游，并要求减少工程量、保留页面美观度，优先通过筛选和名片选项区分群体，明确“不需要区分QQ与微信”。

最终复用现有组队实现，用端游/手游渠道字段隔离名片、招募和相关访问，而不是复制两套页面和后台。这样满足实际匹配差异，也减少重复维护。仅隐藏前端卡片还不够，服务端也要阻止跨渠道混用；可查看[渠道HTTP测试](../tests/teams-channel-http.test.mjs)。

## 四、一次能直接核对到我本人判断的AI纠错

### 场景：GitHub已授权，却仍然无法上传

**当时目标：** 把现有网站整理到自己的GitHub仓库，随后把代码链接放入介绍信。

**AI排查的不足：** 写入出现403后，说明主要停留在“仓库写入权限未生效，需要补授权”，没有及时把“账号授权”和“安装GitHub App并选择仓库”拆开。这个方向过于笼统，反复补同一种授权不一定解决问题。

**我指出的具体差别：** 聊天中的原话是：“问题找到了虽然授权但未安装ChatGPT Codex Connector。”随后我要求协助安装。这是我实际作出的判断，不是后来根据代码补写的经历。

**接下来如何验证：** 工具查询的已安装账号列表起初为空；GitHub页面也显示没有安装。打开OpenAI官方连接器的安装页，限定目标仓库，完成人工授权后，列表出现本人的账号。随后实际写入README成功，再上传完整源码。245个交付文件经远端读取逐项核对一致。

**可以这样口头讲：**

> 我遇到过AI排障说得对但不够具体的情况。GitHub写入403时，它一直往仓库权限方向解释。我注意到已经完成账号授权，但没有安装ChatGPT Codex Connector，于是把这两步分开核对。安装列表为空，安装完成后再实际写文件才成功。我学到的是，把“应该有权限”变成可以检查的状态，最后用真实写入和文件核对验证，而不是只看授权页或者AI说成功。

这是一例**排障判断纠正**，不能包装成我独立修复了GitHub接口代码，或破解了权限限制。安装后的工具操作、上传和哈希核对由AI执行，我提出关键区别并配合完成授权。

## 五、另一个产品验收例子：单方登记结果卡住换人

2026-10-05实操反馈记录有一项具体问题：“服务者单方登记阻碍消费者换人”。如果消费者的权益完全依赖服务者先登记，页面虽然有换人按钮，消费者仍可能走不通流程。

我提供使用反馈后，实现调整为双方都能登记对局开始和提交结果，由另一方核对，不能自报自确认；存在未核对结果时也不能直接确认完成。多人服务时需要相应实际参与者确认。争议保留售后处理入口，不让AI自动裁定。

这里能说明我参与了实际使用和规则判断。代码修改由AI工具辅助完成；不能据此声称我亲自定位了全部源码问题。当时手工验收停在首局换人之后，**没有跑完完整一小时、尾局和全部售后流程**。当前源码和[订单测试](../tests/market.test.mjs)可核对对应保护，但自动化通过不能补写为当年的真人全流程成功。

## 六、面试追问时，应能继续解释的细节

- **为什么等待不计时？** 等待匹配尚未实际服务，开始计时要以必要参与者确认作为业务事件。
- **为什么不能自己报告、自己确认？** 对局记录会影响换人和保障，报告与核对需要分离；争议不能靠页面单方写入变成事实。
- **为什么不让AI自动退款？** AI可以帮助理解材料，金额、权限、订单状态和实际执行仍需确定性规则；当前未接真实支付，更不能宣称AI完成资金处理。
- **为什么不重建免费页面？** 先核对已有成果，只改确认的问题；渠道隔离复用原有流程，减少重复工程和回归风险。
- **怎么知道功能确实工作？** 分别说清实际页面操作、隔离自动化、当前HTTP检查及未执行项。[验证记录](VERIFICATION.md)提供复现入口和局限，测试数量不能替代业务解释。
- **如果被问到不会的源码细节？** 可以准确指出业务规则和相关模块，再现场阅读确认；不要把AI实现的部分说成全部由自己独立设计或编写。

## 七、当前不足与下一步

现阶段较有把握的是需求取舍、原型到持久化业务的推进、反馈闭环和AI协作。仍需补真实参与者跨设备试用、可持续的运营验证，以及经营主体、备案、正式渠道和隐私执行等条件。代码主体仍是JavaScript，核心模块虽已改善排版，模块规模和类型检查仍有改进空间。

我希望把产品想法落实为可运行、可检查的结果，再到真实团队中学习需求调研、协作交付和运营复盘。项目能证明的是已有实践与判断过程，不能仅凭一份讲述文档判断技术深度，也不能用尚未发生的用户、订单或收入补足经历。
